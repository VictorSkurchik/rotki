# Coalesce refresh operations in the engine

The Engine will own Refresh Operation lifecycle and permit at most one active operation that covers the same target. Requests for the same Source coalesce, independent Sources may run concurrently within Engine limits, and a Source request made during a global Refresh joins that covering global operation. A global request made while any Source operation is active is not queued or merged retroactively: it receives typed `409 refresh_conflict / observe_active`, and the caller observes the active collection before offering a later explicit action. A global request with no enabled Source receives `409 no_refreshable_sources / use_full_client` rather than creating a zero-work success. This asymmetric rule is enforced across Full Client and Companion entry points for the Profile. `POST /refresh-operations` additionally requires a caller-scoped `Idempotency-Key`, so an exact retry returns its original operation if the replay record remains retained even when ordinary target coalescing would no longer apply; reusing a retained key with a different payload fails, while a pre-operation target failure creates no replay record. Every successful creation request returns `202 Accepted`, a `Location` for the authoritative operation resource, the operation representation captured at acceptance, and an explicit `coalesced` flag; an idempotent replay returns that original response even after the operation advances. Operations survive Client backgrounding or disconnection, and a returning Client lists active operations and Fetches the current Snapshot before consuming later allowlisted WebSocket notifications rather than starting duplicate work. The stable lifecycle is limited to active `queued` and `running` states and immutable terminal `succeeded` and `failed` states; the Companion protocol has no pause or cancellation operation. Global progress counts the fixed set of selected Sources that have settled, regardless of success, while per-Source progress remains indeterminate in version 1 instead of exposing incomparable provider percentages. A global operation with any failed Source commits successful Source changes and failed-Source last-known data as a Degraded Snapshot before becoming `failed / source_refresh_failed`; it points to that revision, so failure does not imply rollback or absence of effects. Credential rotation, disable, or deletion increments a Source execution generation and fails stale work with `source_configuration_changed`, while rename does not; generation checks discard late writes without blocking Full Client configuration. Terminal entries and their replay records remain in memory for 15 minutes, with at most 256 terminal entries per Profile and oldest-terminal eviction under pressure; active work is never evicted. Closing or locking a Profile is a security boundary: the Engine rejects new Refreshes, fails that Profile's active operations with `operation_interrupted`, cancels their underlying tasks, invalidates access, and clears the Profile-scoped registry before another Profile opens; a lifecycle-generation guard discards every late result from an abandoned task. A controlled Engine shutdown uses the same terminal outcome, while an abrupt restart may discard its disposable operation registry and requires REST and Snapshot reconciliation without inventing a terminal result. Refresh notifications use the existing `{type, data}` envelope and carry a per-operation monotonic version so Clients discard duplicate or older progress, while Snapshot notifications carry only an opaque revision. WebSocket loss never determines operation or snapshot state; REST remains authoritative.
