# Model recoverable failures as data across native boundaries

Expected Companion failures will be explicit variants in shared feature state or feature-specific sealed outcomes rather than thrown exceptions, generic result wrappers, or display strings. Companion HTTP failures preserve the rotki `{result, message}` envelope while adding a required `{code, retryable, action}` error object and semantic non-2xx status; Clients map only those typed fields and never branch on or directly present the redacted diagnostic `message`. The model distinguishes actionable conditions such as Locked Engine, Profile Mismatch, revocation, unreachable network, incompatible Engine Protocol, and per-source Refresh failure; native Clients map those variants to localized presentation. Source Health and targeted Refresh use a closed provider-independent registry for unreachable, rate-limited, authentication, configuration-changed, and unexpected failures, while a global Refresh exposes only an aggregate failure and requires a Snapshot Fetch for Source details. Raw upstream codes, bodies, exception text, and messages never enter the mobile contract. Unknown codes become a typed unexpected Engine or Source failure without discarding an authenticated snapshot, and missing required fields fail the contract. Cancellation remains structured cancellation. An iOS-facing adapter catches any other Kotlin exception before it crosses the Swift boundary, emits a redacted local diagnostic and a typed unexpected-failure state, while invariant failures remain defects covered by tests rather than user-facing control flow.
