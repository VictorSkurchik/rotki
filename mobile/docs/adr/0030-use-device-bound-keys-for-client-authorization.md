# Use device-bound keys for client authorization

Each mobile installation will create a non-exportable P-256 Device Key using the platform security subsystem and register its public key during Pairing as a Base64URL-encoded 65-byte uncompressed X9.63 point. The Engine assigns the registration a stable, uniformly random opaque 256-bit Device Session ID; the ID is used for lookup but grants no authority without proof and reveals neither the public key nor Profile binding. The Client proves possession by signing a 60-second, single-use versioned challenge transcript with ECDSA/SHA-256 and sending a Base64URL-encoded 64-byte P1363 signature; high-S and low-S signatures are accepted, while the Challenge ID is consumed atomically. A successful proof receives a 15-minute Access Session only while its bound Profile is open and may otherwise return a non-data Engine state without creating a session. An Access Session uses a cryptographically random opaque bearer credential held only in Client memory, while the Engine keeps only its hash and authorization metadata in a disposable in-memory store. Foreground renewal is a single-flight fresh Device Key proof begun at five minutes remaining rather than a refresh-token exchange; a transport failure may use the old bearer only until its original expiry. The Client stops using the Engine as soon as it leaves the active foreground and destroys the bearer on background or system lock; returning from background requires device authentication followed by a fresh Device Key proof. The Engine revokes the durable Device Session by atomically removing its registered public key while retaining a permanently non-authorizing audit identity, and neither a Profile password nor a long-lived bearer token is stored on the phone.
