# ExactDecimal characterization

This record preserves the executable P0.2 findings after their M2.1 migration into the
production mobile Gradle build. A project-owned `ExactDecimal` is characterized on JVM,
Android host, and Kotlin/Native against the same checked-in vectors generated by Python
`FVal`.

## Result

Status on 2026-08-13: **passed with a private BigNum workaround**.

All 72 cases produce byte-identical results with Python `FVal` on JVM and
`iosSimulatorArm64`; the `iosArm64` test binary also compiles and links. The cases cover:

- canonical parsing, scientific input, signed zero, scale, and `uint256` maximum;
- comparison, exact addition/subtraction/multiplication, and ordered aggregation;
- terminating and recurring division at 78 significant digits with HALF_EVEN rounding;
- display-only HALF_EVEN rounding and stable numeric sorting;
- JSON string-only serialization;
- malformed, non-finite, over-precision, and out-of-range rejection.

The initial direct use of BigNum 0.3.10 division failed the `2 / 3` vector: it returned a
last digit of `6`, while `FVal` correctly rounds it to `7`. The issue comes from BigNum
comparing an arbitrary integer division remainder as though it were already a discarded
decimal digit. `BigNumDecimalBackend` therefore calculates a 78-digit quotient from the
exact BigInteger numerator/denominator and applies HALF_EVEN itself. The workaround and all
BigNum types stay private; the public `ExactDecimal` API and its serialized form do not
depend on the candidate library.

This is a conditional acceptance of BigNum, not a claim that its raw decimal API is
FVal-compatible. The project-owned type, vectors, and division regression case now live
in `mobile/shared`; only the private backend may be replaced if the workaround or
candidate becomes undesirable.

## Frozen contract

- Input is a JSON string matching
  `-?(?:0|[1-9][0-9]*)(?:\.[0-9]+)?(?:[eE][+-]?[0-9]+)?`.
- Output is minimal plain ASCII: no exponent, redundant zero, trailing fractional zero,
  leading plus, or negative zero.
- Precision is at most 78 normalized significant digits, matching the `FVal` context.
- Addition, subtraction, and multiplication are exact or fail with
  `precision_exceeded`; they never round silently.
- Division is the only lossy domain operation and uses 78 significant digits with
  HALF_EVEN rounding.
- Display rounding is a separate string projection and never changes the stored value.
- Aggregation is an ordered left fold from zero; sorting is numeric and stable.
- The implementation bounds raw input and canonical output to 2048 ASCII characters, an absolute
  written exponent to 1024, and display scale to 30 digits. These denial-of-service guards
  must be reviewed with the transport DTO limits during M2.2.

The canonical source is
[exact-decimal-v1.json](../../shared/test-vectors/exact-decimal-v1.json).
The generated Kotlin constant lets common tests consume the same generated JSON payload
without a JVM-only resource API.

## Reproduce

From the repository root, with Python 3.14:

```bash
uv run python mobile/shared/tools/generate_exact_decimal_vectors.py
```

Regenerate vectors after intentionally changing authored cases or policy:

```bash
uv run python mobile/shared/tools/generate_exact_decimal_vectors.py --write
```

On Apple Silicon macOS with JDK 17 and Xcode:

```bash
cd mobile
./gradlew --no-daemon \
  :shared:jvmTest \
  :shared:testAndroidHostTest \
  :shared:iosSimulatorArm64Test \
  :shared:linkDebugTestIosArm64
```

The device target is linked but cannot run on the host. CI pins Kotlin 2.4.10, Gradle
9.5.0, BigNum 0.3.10, kotlinx.serialization 1.11.0, JDK 17, and Xcode 26.4. The local
acceptance run also passed with Xcode 26.6, outside Kotlin's documented 2.4.10
compatibility row.

## Supersession complete

M2.1 moved the implementation, vectors, generator, and tests into `mobile/shared`. The
disposable nested Gradle root and dedicated workflow were removed in the same change;
`mobile/` is now the only long-lived mobile Gradle root.
